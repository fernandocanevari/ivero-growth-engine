- Contas de agência: tipo em profiles.account_type (gravado pelo trigger de cadastro via metadata); marcas ligadas por agency_brands ao fim do onboarding — por que: mantém o fluxo individual 1:1 intacto.
- Marcas de agência: brand_settings.user_id NULL, criadas só via RPC create_agency_brand; marca ativa em src/lib/brand-scope.ts (brand_id filtra leituras/gravações só para agências) — por que: mantém UNIQUE(user_id) e o fluxo individual 1:1 intactos.
- Faturamento de agência: 1 linha em assinaturas por conta (assinatura-mãe), plano por marca em agency_brands.plano (só service role grava, promovido no pagamento confirmado); desconto de volume em _shared/agency-pricing.ts espelhado em src/lib/agency-pricing.ts — por que: reaproveita idempotência/reconciliação do fluxo individual e gera 1 cobrança só.
- Plano de Ação automático: edge function generate-action-plan (IA + fallback determinístico), disparada sem await após gravar audit_reports; idempotência pela PK de action_plan_generations.audit_report_id e brand_id sempre lido do próprio diagnóstico — por que: falha nunca afeta o diagnóstico e ações de uma marca nunca vazam para outra.
- Agência sem assinatura viva: ProtectedRoute libera /dashboard/marcas e /dashboard/marcas/assinatura e redireciona todo bloqueio para o faturamento consolidado; create-checkout recusa agência sem body.agency (409 agencia_usa_faturamento_consolidado) — por que: agência nunca contrata plano individual fora da assinatura-mãe.
- Guarda de acesso: ProtectedRoute decide via decideAccess (src/lib/access-decision.ts) sobre a linha de assinatura em cache (src/lib/access-cache.ts), derivando o status com a data atual; cache só libera, bloqueio exige dado fresco — por que: navegação rápida sem nunca mostrar página bloqueada nem prender quem tem direito.
- Checkout state is stored in assinaturas.checkout_context and checkout creation is serialized by a service-only database lease before reading the subscription — prevents lost trial history and concurrent payable sessions.
- Asaas fallback examines all subscriptions for a proven customer and adopts only a unique validated candidate; webhook matching is isolated in asaas-webhook/matching.ts — prevents attribution by shared customer alone while keeping manage-subscription behavior unchanged.
- Confirmed payment IDs are counted atomically through record_checkout_payment for webhook and reconciliation — prevents double counting the same paid cycle across delivery paths.
- Proration decisions and invoice lookup are shared only by agency-manage-brand and manage-subscription through _shared/proration.ts; fail closed on lookup errors to avoid duplicate invoices while preserving immediate access.
- Individual upgrade differences ("prorata:<assinatura>:<plano>") are applied only by asaas-webhook/upgrade-payment.ts from the dedicated assinaturas.upgrade_pendente_* columns, never plano_pretendido — renewal RPCs promote plano_pretendido, so reusing it would grant upgrades unpaid.
- Cancellation penalties ("fidelidade:<assinatura>[:<plano>]") live only in assinaturas.multa_pendente_* / multa_ultimo_payment_id; the pending rule is _shared/penalty.ts (mirrored in src/lib/penalty.ts), create-checkout blocks on it, manage-subscription/pay_penalty is the only way to get the invoice, and only asaas-webhook/fidelidade-payment.ts clears it on paid/deleted — keeps the block server-side and lets a deleted charge act as forgiveness without touching status or access.
- The cancellation fee amount has one source: calcularMultaCancelamento in _shared/penalty.ts, used by manage-subscription cancel (persists) and preview_cancel (read-only, feeds the cancel dialog); every code path that changes assinaturas.plano on an annual row must apply snapshotDesconto (old plan) in the same update — so the dialog always equals the charge and cycles paid on an earlier plan keep that plan's discount.
- The paid-access end (assinaturas.data_vencimento) on a confirmed subscription payment comes only from accessEndFromDueDate in _shared/dates.ts (payment.dueDate + 1 calendar month, end of day Brasília, fallback now+30d), used by asaas-webhook and reconcile-asaas — keeps access aligned with the Asaas billing cycle, including days left in a trial paid early.
- Paid reactivation with access left is marked by checkout_context.resumePaidUntil (written only by create-checkout via resumableCancelledAccess); the contract reset is applied only by asaas-webhook resumeSubscriptionPatch in an update conditioned on that marker still present, which claim_subscription_payment clears — so the reset runs once and never after the new subscription's first counted payment.
- Billing display helpers in src/lib/billing-display.ts only mirror paid-resume eligibility and scheduled invoice labels using Brasília calendar days; they never decide access or payments, keeping presentation changes isolated from billing behavior.
- Checkout ID repair is shared by asaas-webhook, reconcile-asaas and manage-subscription through _shared/checkout-binding.ts, routes in order: customer, CPF/CNPJ (GET /customers/{stored} → GET /customers?cpfCnpj → GET /subscriptions?customer per match, unique ACTIVE MONTHLY candidate, same value, on/after checkout day, not bound to another row, max 10 customers), checkoutSession last; writes only provider IDs conditionally — recurring Asaas charges lack checkoutSession and checkout subscriptions do not inherit externalReference, and repairs must never promote access or overwrite a concurrent binding.
- manage-subscription cancel is fail-closed: a non-cancelled row with paid-checkout evidence (checkout_context.completed, status ativo, ciclos_pagos/counted_payment_ids, resumePaidUntil) is cancelled only after a bound/discovered Asaas subscription is deleted or verified gone (GET first); otherwise it returns 200 {ok:false, reason, error} and leaves the row untouched — the card must never keep being charged after a local cancel.
- Individual change_plan prices the difference from planValue(row plano, row ciclo_contratado), never the Asaas subscription value, and an annual row keeps ciclo_contratado "anual" on every path; the upgrade webhook skips the PUT when Asaas already holds the new value and refuses promotion when the plan is already held; closeStaleUpgrade (asaas-webhook/upgrade-payment.ts) best-effort removes a pending upgrade made obsolete by the first recurring charge — after a reactivation with a higher plan Asaas already charges the new value, so reading it made upgrades free.
- Paid-checkout evidence has one definition, hasPaidCheckoutEvidence in manage-subscription/cancel-access.ts, used by cancel (fail-closed) and change_plan (local mode only without evidence, else 200 assinatura_nao_confirmada); UpgradeModal always routes ativo/inadimplente to change_plan, and create-checkout returns 409 assinatura_ativa_use_troca_de_plano instead of reusing a recurring PENDING invoice for a bound ativo/inadimplente individual row — the recurring charge is never a checkout link and a paid row is never promoted for free.
